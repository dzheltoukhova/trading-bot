Architecture

The bot’s processes talk through Redis rather than to each other. The hot path — from a price update to an order on the exchange — stays inside one worker process.

Engineering decisions

How the system stays safe while trading unattended.

Reliability

  • Each execution is counted only once, even if it arrives twice: duplicates are filtered out by execution id, so a replay or reconnect never counts a trade twice.
  • After a WebSocket gap, missed executions are fetched from REST and pushed through the same handler; a longer outage falls back to reconciling against closed positions.
  • When in doubt, it does not trade: if positions or orders cannot be read, entries are blocked rather than allowed.

Risk controls

  • A cap on concurrent trades counts both open positions and orders still waiting to fill.
  • Entry orders that do not fill in time are cancelled; leftover orders are removed as soon as a trade closes.
  • Protective orders cap the worst-case loss of a trade at a set share of the deposit; a sanity check raises an alert if the numbers look wrong.

Concurrency and data

  • Market data is split across four asyncio processes, each holding hundreds of WebSocket subscriptions.
  • Redis is split in two: a disposable cache for hot market data and a persistent store for trades and analytics.
  • Settings change from the web console and reach every process through Redis pub/sub, without a restart.

Testing and operations

  • Tests run against in-memory Redis and a fake exchange; lifecycle tests replay real WebSocket frames recorded on the demo account.
  • Every environment — demo, sub-account, production — runs the same Docker Compose stack from immutable images.
  • Built with AI coding assistants; I own the architecture and personally review all money-critical code.
